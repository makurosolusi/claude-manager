# v0.3.0 spec: Agents page

Status: approved direction ("lanjut spec v0.3.0"), spec by wkr-spec-03. Open questions resolved 2026-11-28 (§8). Builds on v0.2.1 (`fix/v0.2.1-ui-polish`).
User intent: "There's no page yet about the agents I have: their tasks and roles, the model they use, and creating, editing and deleting agents."

Roles stays the usage-analytics page. **Agents** is the management page: one table of every agent Claude Code can delegate to, a detail view, and (phase 2) create/edit/disable/delete for the agents claude-manager owns.

## 1. Facts this spec relies on

### 1.1 Claude Code docs (verified 2026-11-27)
- https://code.claude.com/docs/en/sub-agents
  - Frontmatter: `name` and `description` are required. Optional: `tools`, `disallowedTools`, `model` (`sonnet|opus|haiku|fable|<full id>|inherit`), `color` (`red|blue|green|yellow|purple|orange|pink|cyan`), `permissionMode`, `effort`, `isolation`, `memory`, `maxTurns`, `skills`, `mcpServers`, `hooks`, and others. Unknown fields are ignored. A name has at most 256 chars, no `:`, and doesn't start with `-`. Identity comes from `name`, not the filename.
  - Precedence (highest first): managed settings > `--agents` flag > project `.claude/agents/` > user `~/.claude/agents/` > plugin `agents/`. Plugin agents are named `<plugin>:<agent>`.
  - Built-ins: `Explore`, `Plan`, `general-purpose`, `claude`, `statusline-setup`, `claude-code-guide`, `web-fetch`.
  - **Live effect:** "Claude Code watches `~/.claude/agents/` and `.claude/agents/`. When you add or edit a subagent file on disk … Claude Code detects the change within a few seconds and the next delegation uses the updated definition, with no restart needed." Exceptions: directories added with `--add-dir`/`/add-dir`, and sessions started with `--disable-slash-commands`.
- https://code.claude.com/docs/en/settings: most settings edits reload live. The docs don't say whether an `env` change (`ANTHROPIC_DEFAULT_*_MODEL`) reaches a running session, so tier changes are **out of scope** here (§3.4). If they come back later, the UI must say "new sessions".

UI copy (used in the save notice and the detail footer, `AGENT_LIVE_NOTE`):
> Running Claude Code sessions pick this up within a few seconds: the next delegation uses the new definition. Subagents already running keep the old one. Sessions started with `--add-dir` agent folders or `--disable-slash-commands` need a restart.

### 1.2 Codebase (read for this spec)
- Managed agents come from **config only**: `PRESET_ROLES` (`src/roles/roles.presets.ts`) + `config.customRoles` + `config.roleModels` (a tier or pin per role) + `config.disabledRoles` (`src/config/config.store.ts`). `resolveRoles(config)` (`src/roles/roles.registry.ts`) merges them and **drops disabled ones**.
- Files are written only by `install()`/`reapplyAll()` (`src/install/install.service.ts`): the **same roster goes into every install** in `manifest.installs` (user and/or project). The manifest records each file's sha256 and any backup of a pre-existing file. Removing a role from config makes the next `reapplyAll` delete or restore its file, and `uninstall` reverts exactly what the manifest lists. A file edited by hand is a `conflict`, and `install` throws.
- CLI mutation logic is inline in `src/commands/roles.command.ts` (`set/add/rm/enable`) and `src/commands/tier.command.ts`. That is `saveConfig` then `reapplyAll`, with no dry-run, so a conflict leaves config saved but files stale. Nothing backs up `config.json` today, and `Bun.write` isn't atomic.
- Per-agent routing warnings: `checkRouting()` (`src/commands/doctor.routing.ts`) returns label strings. Only the "project file shadows the role" check is per agent; the rest are global.
- Dashboard: `Bun.serve` on 127.0.0.1, `routes: { "/": index }` (static HTML import, bundled once, **can't be templated**), and `handleApi()` with a Host allowlist that rejects every non-GET (`src/server/dashboard.api.ts`, 114 lines, near the route limit of 150).
- Usage is keyed by role name: `KEY.role` in `src/db/stats.repository.ts` (`agent_type`, or `main`/`subagent`).
- **Rerouted:** not in `src/server/*.types.ts` yet. v0.2.1 is expected to add `requests.requested_model`, with "rerouted" = served `model` ≠ `requested_model`. This spec uses `rerouted_pct: number | null`. `null` means the column doesn't exist yet, and the UI hides the column. W1-repo adapts the SQL to whatever v0.2.1 lands.

## 2. Data model (decided)

One server-side catalog, `src/agents/agents.catalog.ts`, builds `AgentRow[]` from four sources, merged by name:

| Source | Kind | How it's detected | Editable |
|---|---|---|---|
| `PRESET_ROLES` + config | `preset` | name in `PRESET_ROLES` | model (tier/pin), enable/disable |
| `config.customRoles` | `custom` | name in `customRoles` | all fields except name; delete |
| `.md` files in each agents dir that **aren't in any `manifest.installs[*].files`** | `external`, source `file` | dirs scanned: `claudeDir()/agents`, each install's `agentsDir`, `<dashboard cwd>/.claude/agents`; non-recursive; `*.md` ≤ 256 KiB | no ("Not managed") |
| `BUILTIN_AGENTS` constant (§1.1 list) and role names seen in 30-day usage that matched nothing above | `external`, source `builtin` / `plugin` (name contains `:`) / `unknown` | constant + `agentUsage()` keys, excluding `main` and `subagent` | no |

- Disabled presets **are listed** with `status: "disabled"`. Add `allRoles(config)` to `roles.registry.ts`, returning every role with a `disabled` flag. `resolveRoles` stays as it is (it filters `allRoles`).
- `scopes[]` of a managed agent comes from each manifest install: `{ scope, path, state }`, where `state` is `installed` (sha matches), `edited`, `missing`, or `shadowed` (a non-manifest file with the same name exists in a higher-precedence dir). With no installs, `scopes = []` and the UI shows "Not installed".
- External frontmatter: `src/agents/agent.frontmatter.ts` is a minimal parser (`key: value` lines between `---`, JSON-quoted values unquoted, comma lists split). It reads only the fields in `AgentRow`. `// ponytail: line parser, no YAML lists/multiline; swap for a YAML parser if externals render wrong.` No new dependency.
- Plugin agents are **not** scanned from plugin directories. They show up only once used (name with `:`). That is a nice-to-have for later.
- Usage: one grouped query, `agentUsage(db, since)` in `src/db/agents.repository.ts`. It returns `role, requests, cost_usd, unpriced, last_ts, rerouted` for a fixed 30-day window (no N+1, uses `requests_ts`). The catalog joins it in memory.
- The list is small and bounded (≤ presets + customs + dir files). The server returns everything, capped at `MAX_AGENTS = 500` with `truncated: true`, and the table paginates on the client (Rule 13: bounded list, documented cap).

## 3. API

All responses are JSON. Errors use the existing `{ error }` shape. Types go in `src/server/agents.types.ts`:

```ts
export type AgentKind = "preset" | "custom" | "external";
export type ExternalSource = "file" | "builtin" | "plugin" | "unknown";
export interface AgentScope { scope: "user" | "project"; path: string; state: "installed" | "edited" | "missing" | "shadowed" }
export interface AgentUsage { requests: number; cost_usd: number; unpriced: number; last_ts: string | null; rerouted_pct: number | null }
export interface AgentRow {
  name: string; kind: AgentKind; source: ExternalSource | null; status: "enabled" | "disabled";
  description: string | null; color: string | null;
  tier: Tier | null;            // null for externals
  pin: string | null;           // config.roleModels value when it's a model, else null
  alias: string | null;         // opus|sonnet|haiku, or the pin, or the external file's model
  model_id: string | null;      // config.tiers[tier] when tier-routed; the pin when it's a full ID
  tools: string[] | null;       // null = inherit all
  disallowed_tools: string[] | null;
  scopes: AgentScope[]; main_agent: boolean; usage: AgentUsage;
}
export interface AgentsResponse { items: AgentRow[]; truncated: boolean; etag: string; tiers: Record<Tier, string>; known_tools: string[]; warnings: string[]; installed: boolean }
export interface AgentDetail extends AgentRow { prompt: string | null; prompt_source: "config" | "file" | "default" | null; file_path: string | null; warnings: string[]; etag: string }
export type ModelChoice = { tier: Tier } | { pin: string } | { default: true }; // default: presets only
export interface AgentInput { name: string; description: string; model: { tier: Tier } | { pin: string }; tools: string[] | null; prompt?: string }
export type AgentPatch = Partial<Omit<AgentInput, "name" | "model">> & { model?: ModelChoice; enabled?: boolean };
export interface AgentWriteResult { agent: AgentDetail; applied: number /* installs re-applied */; etag: string }
export interface SessionInfo { write: boolean; token: string | null }
```

| Method & path | Body | Success | Errors |
|---|---|---|---|
| `GET /api/agents` | | 200 `AgentsResponse` | |
| `GET /api/agents/:name` | | 200 `AgentDetail` | 404 `agent "x" not found` |
| `GET /api/session` | | 200 `SessionInfo`, `Cache-Control: no-store` | |
| `POST /api/agents` | `AgentInput` | 201 `AgentWriteResult` | 400, 409 |
| `PATCH /api/agents/:name` | `AgentPatch` | 200 `AgentWriteResult` (a no-op patch still returns 200) | 400, 404, 409 |
| `DELETE /api/agents/:name` | | 200 `{ removed: name, applied, etag }` | 404, 409 |

Every write also needs the guard (§4) and `If-Match: <etag>`: 428 when missing, 412 `config changed outside this page; reload` when stale. `etag` = sha256 of the `config.json` text, or `"none"`.

### 3.1 Validation (400 messages; reuse the CLI messages where they exist)
- `name`: `assertRoleName` (`/^[a-z][a-z0-9-]{0,39}$/`), which is stricter than the docs and fine. The name can't be changed after create (rename is a nice-to-have).
- `description`: required, trimmed, 1–1000 chars: `description is required (Claude uses it to pick the agent)`.
- `model.tier` → `isTier`. `model.pin` → `/^[\w.\-:\[\]]+$/`, same as `roles set`.
- `tools`: `null` = all except Agent (CLI default). An array goes through `assertTools` (KNOWN_TOOLS, `Tool(...)`, `mcp__*`), deduped, 1–64 entries.
- `prompt`: optional, ≤ 20,000 chars. Empty means the default `You are the <name> specialist. <description>`.
- Presets: a patch may only contain `model` and `enabled`, otherwise `preset agents only allow model and enabled`. `enabled` is preset-only (customs are deleted, not disabled): on a custom → 400 `custom agents have no enabled state; delete it instead`. Externals: any write → 409 `"x" is not managed by claude-manager; edit <path> directly`.
- Unknown body keys → 400 `unknown field "x"`.

### 3.2 Conflicts (409)
- Create: the name is a preset or custom (`role "x" already exists`), a `BUILTIN_AGENTS` name (`"x" is a Claude Code built-in agent name`), or an external file with that name in an install's agents dir (`<path> exists and isn't managed by claude-manager`).
- Delete or disable the main agent: the CLI message (`"x" is the main agent at …`).
- DELETE on a preset: `presets can't be deleted; disable it with PATCH {"enabled":false}`. The UI shows Disable instead.
- A dry-run finds a hand-edited managed file: `these files were edited by hand: … Run "claude-manager install --force" to overwrite (a backup is kept).` Nothing is written.

### 3.3 Write path: shared service (Principle 1)
Pull the logic out of the command files so the CLI and the API call the same functions:
- `src/roles/roles.service.ts`: pure config transforms that throw `CliError` with a reason. `addRole(config, input)`, `updateRole(config, name, patch)` (new: edits a custom role's description/tools/prompt/tier), `setRoleModel(config, name, choice)`, `removeRole(config, name, manifest)` (custom → delete, preset → disable), `enableRole(config, name)`, `setTierModel(config, tier, model)`.
- `src/config/config.apply.ts`: `applyConfig(next)`, used by both CLI and API:
  1. Run `withConfigLock` (an in-process promise chain; `// ponytail: in-process lock; cross-process races are caught by the etag`).
  2. Dry-run `install(target, next, { dryRun: true, mainAgent })` for every manifest install. Any `conflict` → 409, nothing written.
  3. Back up the current `config.json` to `backupPath("config.json")` (same folder and naming as the install backups; `uninstall --purge-data` removes them).
  4. Write `config.json` atomically (tmp file + `rename` in `json.file.ts`).
  5. `reapplyAll(next)`. On an I/O error, restore the backed-up config and rethrow with context (`apply config: <cause>`) → 500.
- `CliError` gets an optional third argument `reason: "invalid" | "not_found" | "conflict"`, which the API maps to 400/404/409 (the default is 400). The exit code is unchanged.
- `roles.command.ts` / `tier.command.ts` become thin wrappers: parse args → service → `applyConfig` → print. **`test/roles.test.ts` must pass unchanged.** The CLI gains the dry-run safety for free.
- Deleting a custom role removes it from config. `reapplyAll` then removes the file, or restores the user's original backup, because the role is no longer desired. `uninstall` therefore stays exact, with no new code.

### 3.4 Tier model editing, and what is not in v0.3.0
- **Tier model editing** (`PUT /api/tiers/:tier`, `GET /api/tiers`, editing on the tier cards). **Reversed on 2026-11-28 by owner request: it ships in v0.3.0.** The earlier decision was to leave it out because the docs did not confirm whether an `env` change in `settings.json` reaches running sessions. The env-vars doc now says: "A running session applies new and changed values to its environment when you save the file" (https://code.claude.com/docs/en/env-vars). That does not guarantee the switch on the next request, so the UI does not promise "within seconds". Shipped copy: "Applies to new Claude Code sessions; running sessions reload settings and may switch on their next request — restart them to be sure." `tier set` prints the same note.
- Not in v0.3.0: rename, colour picker for custom agents, editing preset prompts, writing external files, scanning plugin directories, per-scope agents (claude-manager writes the same roster to every install).
- Rename, colour picker for custom agents, editing preset prompts, writing external files, scanning plugin directories, per-scope agents (claude-manager writes the same roster to every install).

### 3.5 `roles edit` (CLI, same service as PATCH)
Added in wave D2 (§6). It builds the same `AgentPatch` object that `PATCH /api/agents/:name` receives, then calls `updateRole()` and `applyConfig()`. The two surfaces therefore produce the same `config.json` and the same installed files.

```
claude-manager roles edit <name> [flags]
  --description <text>        "When to use" text (presets and customs)
  --tier <think|work|basic>   Route to a tier          → model: { tier }
  --pin <model>               Pin an alias or full ID  → model: { pin }
  --default                   Remove the override      → model: { default: true } (presets only)
  --tools <A,B,...|all>       Allowlist; "all" = all except Agent → tools: null
  --prompt-file <path>        System prompt from a file (empty file = default prompt); --prompt-file avoids shell quoting of long prompts
  --enable | --disable        Presets only              → enabled: true | false
```

- `--tier`, `--pin` and `--default` are mutually exclusive, and so are `--enable` and `--disable`. Any other combination → usage error.
- Style follows `roles add` (`node:util` `parseArgs`, `CliError` for bad input, `save` + re-apply). Validation lives in the service, so the messages match §3.1 exactly.
- Parity exception (only one): `roles edit <name>` with no flags prints usage and exits 1; `PATCH {}` returns 200. Neither writes anything.

## 4. Security

### 4.1 Threat model
1. Any website open in the browser can send `fetch("http://127.0.0.1:5757/api/agents", {method:"POST"})`. Simple requests go out without a preflight, and the Host check passes.
2. DNS rebinding: a foreign page re-points its name to 127.0.0.1. The existing Host allowlist blocks it.
3. A cross-site page can't read responses (no CORS headers are ever set), so it can't read the token.
4. Other local processes or users can already write `~/.claude` directly. They are out of scope.
5. Impact if broken: an attacker writes the agent prompt or tools that Claude Code then runs (code execution through the agent). **High**, so every write is gated.
6. Not covered: browser extensions with host permissions, or malware on the machine.

### 4.2 Controls (new `src/server/write.guard.ts`, used for every non-GET under `/api`)
Checks run in this order. The first failure returns, and nothing is read or written:
1. Existing Host allowlist → 403 `forbidden host`.
2. Method must be POST/PATCH/DELETE on a known write route, else 405. OPTIONS → 405 (no CORS, so a cross-origin preflight fails).
3. Read-only mode → 403 `dashboard is read-only (started with --read-only)`.
4. `Origin` must equal `http://127.0.0.1:<port>` or `http://localhost:<port>`. A missing Origin → 403 `forbidden origin`; browsers always send it on these methods.
5. When present, `Sec-Fetch-Site` must be `same-origin` → 403.
6. `X-CM-Token` must equal the process token, compared with `crypto.timingSafeEqual` on equal-length buffers → 403 `missing or invalid token`.
7. POST/PATCH need `Content-Type: application/json` (charset allowed) → 415. DELETE has no body.
8. Body ≤ 64 KiB: check `Content-Length`, then cap the bytes actually read (chunked bodies) → 413. Invalid JSON → 400 `invalid JSON body`.

Token: `crypto.getRandomValues` 32 bytes, hex, generated in `dashboard.command.ts` at process start. It isn't persisted or logged. The page fetches it from **`GET /api/session`** once at boot. It can't be baked into `index.html`, because the HTML import is bundled once and served statically. That endpoint is safe: it goes through the Host check, and cross-origin pages can't read it (same-origin policy). A custom header (`X-CM-Token`) also forces a preflight, which fails. A restart gives a new token, and a 403 `invalid token` in the UI makes the client re-fetch `/api/session` once and retry.

### 4.3 Read-only flag (decided)
Writes are **on by default** (decided 2026-11-28). `claude-manager dashboard --read-only` turns them off. Reason: the dashboard only listens on 127.0.0.1, and every write needs the per-process token, a same-origin `Origin`/`Sec-Fetch-Site`, and a JSON body, so default-on is safe. Default-off would make people remember a flag every time they edit.

In read-only mode:
- `/api/session` returns `{ write: false, token: null }`, and every POST/PATCH/DELETE gets 403 `dashboard is read-only (started with --read-only)`.
- The UI hides New, Edit, Delete, Disable and Enable, and the form routes (`?new=1`, `?edit=1`) redirect to the detail. A "Read-only" badge in the page header states the reason: "Started with --read-only. Restart without it to make changes."
- Usage text: drop "read-only dashboard" and document the flag. No config key (a nice-to-have).

It auto-dismisses after 8s and has a close button. Error notices use `role="alert"` and stay until dismissed. After create, go to `#/agents/<name>`. After delete, go to `#/agents` with the notice.
- Client write helper `lib/api.write.ts`: `sendJson(method, path, body?, etag)` adds `X-CM-Token`, `If-Match` and `Content-Type`. On 403 `invalid token` it re-fetches `/api/session` and retries once. Errors are rethrown with method, path, status and message (same pattern as `getJson`).

## 7. Acceptance criteria (check in the browser unless marked CLI/curl)
1. At 1440 and 390, the nav shows 6 items with no horizontal scroll; Agents is 4th; `#/agents` is active.
2. `#/agents` lists the 6 presets (solid badges), customs and externals (outline). Kind facet counts match the seed. The Explore/general-purpose built-ins show as External, "Not managed", with no actions.
3. The model chain for `coder` reads `work → sonnet → claude-sonnet-5-5`. After `claude-manager roles set coder fable` (CLI) and a reload, it shows the pin icon and `fable`.
4. Usage columns match Roles → By role for the 30-day range (requests, cost). Rerouted is hidden when there's no data.
5. Detail shows the prompt, tools, every install path with its state, and a shadow warning when `.claude/agents/coder.md` is hand-placed in the dashboard cwd.
6. **Security (curl):**
   - `curl -X POST -H 'Content-Type: application/json' -d '{}' http://127.0.0.1:5757/api/agents` → 403;
   - the same with a valid token and `-H 'Origin: https://evil.example'` → 403;
   - with a valid token and `Content-Type: text/plain` → 415;
   - from a page on another origin, `fetch(..., {method:"POST"})` fails (403 or preflight error) and nothing changes on disk.
7. Create `ui-ux` (tier work, tools Read/Grep/Glob/Edit/Write, description set) from the form. The notice shows "applied to N installs" plus the live note. `claude-manager roles` (CLI) prints `ui-ux  work  sonnet -> claude-sonnet-5-5  custom  Read,Grep,Glob,Edit,Write`, and `~/.claude/agents/ui-ux.md` exists.
8. Edit `ui-ux`'s prompt, then navigate away without saving → the "Discard unsaved changes?" dialog appears. Save → the file changes and `config.json`'s previous version is in `~/.claude-manager/backups/`.
9. Hand-edit `ui-ux.md`, then save from the dashboard → 409 banner with the `install --force` hint; config is unchanged.
10. Delete `ui-ux` (native dialog) → the file is gone and the CLI no longer lists it. Disable `writer` → the file is gone, the row shows Disabled, and Enable restores it.
11. Create `ui-ux` again, then run `claude-manager uninstall` → `ui-ux.md` is removed and `doctor` reports nothing left over.
12. **Read-only UI (browser):** `claude-manager dashboard --read-only` → the list has no New button, the detail has no Edit/Disable/Enable/Delete, `#/agents?new=1` and `?edit=1` redirect to the detail with a notice, the header shows the "Read-only" badge with its reason, and the tier cards still show, without an Edit button.
13. **Read-only API (curl):** with `--read-only` and a valid token and Origin, `POST /api/agents`, `PATCH /api/agents/coder` and `DELETE /api/agents/ui-ux` each → 403 `dashboard is read-only (started with --read-only)`; `GET /api/session` → `{"write":false,"token":null}`; no file or `config.json` changes.
14. Restart the dashboard while a tab is open, then save → the client re-fetches the token and the save succeeds without a manual reload.
15. **`roles edit` parity (CLI):** for `coder` (preset) and `ui-ux` (custom), run `claude-manager roles edit <name> …` and, on a second temp HOME, `PATCH /api/agents/<name>` with the equivalent body. `config.json` and every installed file are byte-identical. Covered cases: `--pin fable`, `--default`, `--enable/--disable`, `--tier basic`, `--tools all`, `--prompt-file`. `roles edit coder --description x` → `preset agents only allow model and enabled` (CLI exit 1, API 400 with the same text).

## 8. Decisions (user-approved 2026-11-28)
1. **Writes on by default.** `claude-manager dashboard --read-only` turns them off. The UI hides or disables create/edit/delete and shows the reason; the API returns 403 with a clear message (§4.3, acceptance 12–13).
2. **`claude-manager roles edit` ships in v0.3.0.** It uses the same `roles.service.ts` as `PATCH /api/agents/:name`, with flags that match the PATCH fields (§3.5). It is covered by the parity test and acceptance 15 (wave D2).
3. **Tier model editing was reversed into v0.3.0 on 2026-11-28 at the owner's request.** It was previously deferred; see §3.4.
