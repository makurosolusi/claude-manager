# 05 — v0.2.0 Spec: Colour, Icons, Table Toolkit, Remaining Pages

Status: draft for user approval · Branch: `feature/v0.2.0-dashboard` · Extends `PLAN/04-ui-design-spec.md` (tokens, shell, DataTable, Overview/Sessions). Anything not restated here stays as in 04.
Verified against: `db.schema.ts` (user_version 1), `dashboard.repository.ts`, `stats.repository.ts`, `dashboard.api.ts`, lucide-react **1.82.0** (installed), `@tanstack/react-table` npm latest **9.3.1** (2026-10-12, MIT, peer `react >=18`).

**Three rules that hold everywhere**
1. **Hue means model family. Nothing else gets a family hue.** Tiers have no palette of their own (see §1.3).
2. **Colour is never the only cue.** Every coloured mark sits next to an icon or a text label; status/role/tier badges are always icon + text.
3. **Text uses text tokens** (`foreground`, `muted-foreground`, or a `*-fg` token on its matching `*-bg`). Mark colours (`--model-opus` etc.) are only for dots, bars, and chart fills.

## 1. Colour system (`src/web/index.css`)

Tokens are written as **hex** (exact, gamut-safe; OKLCH given for reference). Each category has 4 tokens: mark `--x`, text `--x-fg`, tint `--x-bg`, outline `--x-border`. Register all of them in `@theme inline` as `--color-…` so classes like `bg-model-opus-bg text-model-opus-fg border-model-opus-border` exist. Components never build class names dynamically: `lib/color.tokens.ts` holds full static class strings per key.
Surfaces used to validate: light card `#ffffff`, dark card `#101010` (`oklch(0.175 0 0)`), dark background `#0a0a0a`.

### 1.3 Tier vs model (overlap resolved)

**Rule: a tier wears the colour of the model family it is configured to (`/api/meta` `tiers`) and has its own icon.** `think`→`Brain`, `work`→`Hammer`, `basic`→`Zap`, `other`→`CircleHelp` (neutral).
With default config this gives think = opus blue. If the user sets `think=sonnet`, the think badge turns orange. Colour therefore always answers "which model family", and the icon + word answers "which tier". No `--tier-*` tokens exist, so two colour systems can never disagree. `TierBadge({ tier, tiers })` resolves the colour via `modelFamily(tiers[tier])`.

## 3. Table toolkit

**Decision: extend our own `DataTable`; do not add `@tanstack/react-table`.**
- The big tables (Sessions, Requests) are server-side, so TanStack would run in "manual" mode for sort, filter, pagination and grouping. It would contribute nothing but state plumbing.
- The client tables are under 200 rows and need about 60 lines of pure functions.
- v9 is a fresh major with a changed API, and our current DataTable already has the header, sort, states and responsive logic.
- Zero new dependencies.

Popovers use the **native HTML Popover API** (`popover` + `popoverTarget`, which React 19 supports): top layer, light-dismiss and Esc come for free. Selects (group-by, page size, sort on mobile) are native `<select>`.

### 3.3 Server vs client, and grouping

| Table | Mode | Why |
|---|---|---|
| Sessions | **server** (filters, facet counts, sort, page, groups) | unbounded |
| Session → Requests | **server** | can be thousands per session |
| Projects | client, one fetch `pageSize=200` | dozens; >200 → note "Top 200 projects by cost" |
| Roles (role×model), By model, By role | client from one `/api/roles?pageSize=200` | role×model is small |
| Live | client (`/api/live`, ≤20 rows) | bounded by `LIVE_LIMIT` |

**Grouping for server-paginated data = aggregate-first.**
1. With `group≠none` the table fetches `GET …/groups?by=X&<same filters>`. Each group carries its `count` and usage totals computed by SQL over **every** matching row, so subtotals never cover only one page.
2. Groups render collapsed. Group-level paging is client-side over at most `MAX_GROUPS = 100` groups using the same TablePagination.
3. Expanding a group fetches the rows with the group value as an extra filter: `…?<filters>&X=<key>&pageSize=10`. The group footer reads "Showing 10 of 37 · Show all →", which sets that filter and `group=none`.

Correctness follows because the groups query and the rows query share one WHERE builder. A test asserts Σ group counts = list `total` and Σ group cost = Σ cost over all pages.
Group-by dimensions must be single-valued per row (otherwise sums double-count). For that reason Sessions groups by `project | family | status`, where family = the session's **primary** model family, the same thing the Model column shows. `role` is a filter only, because a session has many roles. Roles grouping lives on the Roles page.

**Facet counts** follow standard faceted search: the counts for dimension D apply every active filter except D's own. That is one GROUP BY per dimension (4 small queries), only when `facets=1`.
**Limits:** pageSize ≤ 200 (existing `MAX_PAGE_SIZE`); UI offers 25/50/100. Group rows preview at 10. ≤20 values per facet param, each ≤512 chars. Project facet returns the top 50 by count. No query inside loops. Primary model is one window query over the filtered sessions, not per row. `ponytail:` primary-family filter/group scans the window's requests; materialise `sessions.primary_model` at ingest if requests exceed ~1M.

## 4. API changes

All params are validated in `dashboard.params.ts` (+ `filter.params.ts`). Unknown enum value, too many values, or too long → **400** `invalid <name> "<v>": use one of …`. List values bind as JSON arrays: `col IN (SELECT value FROM json_each($list))`, with `$list IS NULL` = no filter. Repeated keys are read with `searchParams.getAll`.

### 4.1 Shared filter changes
- `StatsFilter` gains `projects?: string[]` (**exact** `project_cwd` match). The dashboard's `project` param becomes repeatable and exact. The CLI `stats --project` keeps substring `project`. `WHERE` gets `AND ($projects IS NULL OR s.project_cwd IN (SELECT value FROM json_each($projects)))`.
- Constants in `dashboard.types.ts` (shared with the web): `FAMILIES = ["opus","sonnet","haiku","other"]`, `SESSION_STATUSES = ["live","idle","ended"]`, `SESSION_STATUS_MIN = { live: 5, idle: 15 }`, `SESSION_GROUPS = ["project","family","status"]`, `REQUEST_GROUPS = ["agent","family","stop"]`.
- SQL helper `FAMILY_SQL(col)` = `CASE WHEN instr(lower(col),'opus') THEN 'opus' WHEN … 'sonnet' … 'haiku' ELSE 'other' END`. It mirrors `modelFamily()`, and a test keeps the two in sync.

### 4.2 Sessions
```
GET /api/sessions?since&q&sort&dir&page&pageSize&project*&family*&role*&status*&facets=1
  → SessionsResponse = Page<SessionRow> & { facets?: SessionFacets }
GET /api/sessions/groups?by=project|family|status&<same filters, no page/sort>     (matched BEFORE /api/sessions/:id)
  → { by: SessionGroupBy; groups: GroupRow[]; total_groups: number }   // ≤ MAX_GROUPS, ordered cost desc
interface FacetCount { value: string; count: number }                  // count = sessions
interface SessionFacets { project: FacetCount[]; family: FacetCount[]; role: FacetCount[]; status: FacetCount[] }
interface GroupRow extends Usage { key: string; count: number; last_ts: string | null }
```
- `family`: the session's primary model (existing `MAIN_MODEL` ordering) mapped by `FAMILY_SQL`.
- `role`: `EXISTS (SELECT 1 FROM requests r LEFT JOIN agents a … WHERE r.session_id = s.id AND KEY.role IN …)`.
- `status`: derived from `s.last_ts` vs server `now` (`sessionsPage(db, f, p, q, now = Date.now())` so tests can pass `now`).
- Usage totals are whole-session (same as rows), so Σ rows = group total.
- The Overview top-5 call omits `facets` (no extra queries).

### 4.3 Session detail
```
GET /api/sessions/:id → SessionDetail & { models: UsageRow[] /*key=model*/; tools: { name: string; calls: number }[]; compactions: number; context: { used: number; window: number } | null }
GET /api/sessions/:id/requests?page&pageSize&sort=ts|cost|tokens|context&dir&family*&agent*&stop*&tool*&facets=1
  → Page<RequestRow> & { facets?: { family: FacetCount[]; agent: FacetCount[]; stop: FacetCount[]; tool: FacetCount[] } }
GET /api/sessions/:id/requests/groups?by=agent|family|stop&<filters> → { by; groups: GroupRow[]; total_groups }
interface RequestRow extends Omit<Usage, "requests" | "unpriced"> { message_id: string; ts: string; model: string; agent_id: string | null;
  role: string /* KEY.role */; stop_reason: string | null; tools: string[]; context: number /* input+cache_read+cache_5m+cache_1h */ }
```
- Sort defaults: `ts desc`. Tiebreak `message_id`.
- `agent` values are role keys (`main`, `coder`, …).
- `stop` accepts `none` for NULL.
- `tool` filter: `EXISTS (SELECT 1 FROM tool_calls tc WHERE tc.message_id = r.message_id AND tc.name IN …)`.
- `tools` per row: `group_concat(DISTINCT tc.name)` over the page subquery only.
- `context` reuses `contextWindow()` and the live CONTEXT expression on the latest main-agent request.
- Unknown session → 404 on all three endpoints.
- The existing `/timeline` stays; it only changes its pager on the client.

### 4.4 Meta, favicon
- `DashboardMeta` gains `roles: { name: string; tier: Tier; source: "preset" | "custom" }[]` from `resolveRoles(config)` in `dashboard.command.ts`. `NO_META` returns the presets.
- `GET /favicon.svg` and `GET /favicon.ico` serve one inline SVG constant (`src/server/favicon.ts`): a 10px rounded square in brand `#0169cd`, plus a `@media (prefers-color-scheme: dark)` fill `#3ba6f5`, `image/svg+xml`, `Cache-Control: max-age=86400`. `index.html` gets `<link rel="icon" type="image/svg+xml" href="/favicon.svg">`.
- `/api/projects`, `/api/roles`, `/api/live` and `/api/overview` keep their response shapes (`project` exact semantics only).

### 4.5 Migration (MIGRATIONS[1], user_version 1 → 2; indexes only, no data change)
```sql
-- v0.2.0: new filters/facets scan sessions by last_ts/project and count agents/tools per session; without these each is a full scan.
CREATE INDEX IF NOT EXISTS sessions_last_ts ON sessions(last_ts);
CREATE INDEX IF NOT EXISTS sessions_project ON sessions(project_cwd, last_ts);
CREATE INDEX IF NOT EXISTS agents_session ON agents(session_id);          -- SESSION_GROUPED agent count subquery
CREATE INDEX IF NOT EXISTS tool_calls_session ON tool_calls(session_id, name);
```
**Rollback:** a v0.1.0 binary refuses a v2 DB ("newer than this claude-manager"). Because the change is indexes only, `PRAGMA user_version = 1` restores compatibility. Document this in the CHANGELOG under Changed.
