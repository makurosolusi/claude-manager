# v0.4.0 spec: Permission policy

Status: decisions approved by owner on 2026-11-28 ("setuju"), see §11. Spec by wkr-spec-04. Builds on v0.3.0 (`feature/v0.3.0-agents`).
User intent (paraphrased): "Workers under the manager keep asking me for permission even though a manager already manages them. The chain of authority is owner → manager; after that the manager decides, because the manager answers to me. Workers' permissions should follow the manager's. It must also be in the GUI as a button, so I can't forget to set it up."

claude-manager gets a **permission policy**: the owner picks a preset once (or edits a per-role matrix). claude-manager writes a small owner mandate into Claude Code settings (owner-only actions always `ask`, secrets always `deny`) and registers one PreToolUse hook. The hook is the same binary. It answers allow/ask/deny per role, so a background `coder` can edit and run tests without a prompt, while `git push` still reaches the owner.

## 1. Facts this spec relies on

### 1.1 Claude Code docs (verified 2026-11-28)
- https://code.claude.com/docs/en/sub-agents
  - `permissionMode`: `default`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`, `plan`, `manual` (= `default`). "Ignored for plugin subagents." Unset = inherits the main conversation's mode.
  - "When the main conversation is in `bypassPermissions`, `acceptEdits`, or auto mode, your subagent runs in that same mode and Claude Code ignores the `permissionMode` you set." Parent in `plan` → the subagent stays in plan. Parent in `default`/`dontAsk` → the subagent's own `permissionMode` applies.
  - "When a background subagent reaches a tool call that needs permission, Claude Code surfaces the prompt in your main session and names the subagent that is asking." "A message from an agent doesn't count as your approval for a pending permission prompt." So the parent agent can't approve for a worker. Only the human, rules, modes or hooks can.
  - "Hooks from settings files … also run inside subagents. Tool events such as `PreToolUse` and `PostToolUse` fire for the subagent's tool calls the same way they do in the main conversation."
  - Built-in subagents "inherit the parent conversation's permission rules".
- https://code.claude.com/docs/en/permissions
  - "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome." "If a tool is denied at any level, no other level can allow it."
  - "PreToolUse hook decisions don't bypass permission rules. Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns: a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned `"allow"`."
  - Compound commands: "Deny and ask rules apply when any subcommand matches them, including a command nested inside a subshell, a command substitution, or a control-flow body." An allow rule needs every subcommand to be allowed.
  - Bash rules "match the command text … [and are] not a security boundary around the program" (e.g. another invocation form of the same program isn't matched).
  - `:*` = trailing wildcard, only at the end (`Bash(ls:*)` ≡ `Bash(ls *)`).
  - Modes: `dontAsk` "auto-denies every call that would otherwise prompt"; allowed tools still run. `permissions.denyInsteadOfPrompting` (user or managed settings) denies instead of prompting in any mode. `disableBypassPermissionsMode` "works from any scope".
  - Plan mode: a PreToolUse `"allow"` "has no effect on a file edit or another call that isn't read-only".
  - Managed `allowManagedPermissionRulesOnly` makes managed settings the only source of rules.
- https://code.claude.com/docs/en/settings
  - Precedence: managed > command line (`--settings`) > project local > shared project > user. "When you set the same list key, such as `permissions.allow`, in more than one file, Claude Code combines the lists."
  - "`permissions.defaultMode` values `auto` and `bypassPermissions` don't take effect from project or local settings."
  - Live reload: "it applies most edits to the running session without a restart, including edits to `permissions`, `hooks`".
  - Shared `.claude/settings.json` `allow` rules wait for workspace trust; `deny`/`ask` apply right away. `settings.local.json` allow rules don't wait while it is untracked. Claude Code reads the local file at the **repository root**.
- https://code.claude.com/docs/en/hooks
  - Common input: `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, `agent_id` ("the subagent … the hook fires in"), `agent_type` ("Present when the session uses `--agent` or the hook fires inside a subagent"). PreToolUse adds `tool_name`, `tool_input`, `tool_use_id`.
  - Output: `hookSpecificOutput.permissionDecision` = `allow` ("skips the permission prompt, except for actions no mode auto-approves"), `deny`, `ask`, `defer` (`-p` only). `permissionDecisionReason` is shown to the user for `ask` and to Claude for `deny`. Multiple hooks: `deny > defer > ask > allow`.
  - Exit 0 with no output = "no decision … the normal permission flow". Exit 2 blocks. Any other failure (crash, can't start, invalid JSON, timeout) is non-blocking: "the action goes ahead" through the normal flow, unless `"onFailure": "block"` is set (v2.1.295+).
  - `timeout` default 600 s for command hooks. Matching hooks run in parallel. "If you define the same handler in more than one settings file, it runs once."
  - **Exec form**: with `args` present, `command` is spawned directly with no shell. Without `args`, the shell (`sh -c`) runs it.
  - PermissionRequest exists (`decision.behavior` allow/deny). It fires only when Claude Code is about to prompt. Its docs don't mention subagents (§1.3).
  - `disableAllHooks`; managed `allowManagedHooksOnly` blocks user/project/local hooks.

### 1.2 What this means for the design
1. A PreToolUse hook is the only documented way to say "this worker may do X without asking" **per role**. Settings rules are session-wide, and `permissionMode` is ignored whenever the owner's session is in acceptEdits/auto/bypass.
2. Settings `ask`/`deny` rules beat any hook `allow`. So the owner mandate (push = ask, secrets = deny) goes into **settings rules**, and the hook can't undo it, even if the hook has a bug.
3. A hook failure falls back to the normal permission flow, which means a prompt. That is safe because the hook only *adds* permissions. The protective floors live in settings (§4.4).
4. `defaultMode` isn't needed to stop worker prompts. It is an optional extra (§2.5).

### 1.3 Not verified (treated as unknown; the design doesn't depend on them)
- Whether PermissionRequest fires for subagent calls, and with `agent_type`. Not used in v0.4.0.
- Whether settings `ask` rules still prompt in `bypassPermissions`. Doctor warns when bypass is the default (§7).
- Whether a hook `allow` skips the auto-mode classifier.
- Whether `Read(...)` deny rules also stop `cat .env` through Bash. The hook denies such Bash calls for workers anyway (§4.3).
- The exact `matcher` syntax for alternation (`Edit|Write`) and the minimum Claude Code version for exec form `args`. W2 verifies both against the installed `claude` (§8). Fallback: matcher `"*"` and a shell-form command with a single-quoted absolute path.
- The managed settings paths (`/Library/Application Support/ClaudeCode/managed-settings.json`, `/etc/claude-code/managed-settings.json`). W2 confirms them.

### 1.4 Codebase (read for this spec)
- `settings.merge.ts` handles scalar keys only (`"<section>.<key>"`). `setKey("permissions.allow", …)` would replace the user's whole list, so list entries need new entry-level tracking (§2.3).
- `install()` takes a settings backup only on the first install. `uninstall()` reverts the keys. If the result deep-equals the backup, it writes the backup bytes back, which is how "byte-identical" already works for `env`.
- `applyConfig()` gives a lock, a dry-run, a config backup, an atomic write and rollback. `write.guard.ts` gives Host, Origin, `Sec-Fetch-Site`, token, JSON and size checks plus `--read-only`. The etag is the config.json sha256.
- `dashboard.api.ts` is 138 lines (limit 150) and `overview.page.tsx` is 150. Both owners in §8 must extract code rather than grow these files.
- The nav has 6 items in a `grid-cols-6` row at 390.

## 2. Data model

### 2.1 Capabilities and decisions
| Capability | Tool calls it covers | Notes |
|---|---|---|
| `read` | Read, Grep, Glob, LSP | Mostly no prompt anyway inside the working dir |
| `edit` | Edit, Write, NotebookEdit **inside the project dir** | Outside the project, or `.git/`, `.claude/`, secret paths → no allow (§4.3) |
| `test` | Bash matching `policy.testCommands` (default `bun test`, `bun run test`, `bun run build`, `bunx tsc`, `npm test`, `npm run test`, `npm run build`, `pnpm test`, `yarn test`, `cargo test`, `go test`, `pytest`) | Only simple commands (§4.3) |
| `shell` | Any other Bash | |
| `web` | WebFetch, WebSearch | |
| `agents` | Agent, SendMessage, TaskStop | Spawning and steering workers |
| `git` | Bash `git add/commit/switch/checkout/restore/stash/branch` | Local history only |
| `push` | `git push`, publish, deploy, release | **Owner-only**: `ask` or `deny`, never `allow` |
| `mcp` | `mcp__*` | |

Decision per cell: `allow` | `ask` | `deny` | `default` (no hook decision; Claude Code's own mode and rules decide). Secrets aren't a capability: they are always denied for every row (§4.4).

### 2.2 Config (`config.json`, new optional key)
```ts
export type Capability = "read" | "edit" | "test" | "shell" | "web" | "agents" | "git" | "push" | "mcp";
export type Decision = "allow" | "ask" | "deny" | "default";
export type PresetName = "strict" | "balanced" | "autonomous";
export interface PolicyConfig {
  enabled: boolean;
  preset: PresetName;
  scope: "user" | "project";
  projectDir?: string;                                        // scope=project only; absolute
  overrides: Record<string, Partial<Record<Capability, Decision>>>; // role name | "main" | "unknown"
  defaultMode?: "acceptEdits" | null;                         // §2.5; null/absent = don't write it
  testCommands?: string[];                                    // ≤ 32 entries, each ≤ 80 chars
}
// Config gains: policy?: PolicyConfig   (absent = never set up)
```
Effective matrix = preset row (by role name for presets, by tier for customs) + `overrides`. Rows: `main` (the owner's own session), every enabled role, `unknown` (built-ins, plugin and external agents). One pure function, `effectivePolicy(config)`, serves the CLI, the API, the UI and the compiler.

Presets (P = presets, C = customs by tier; `push` is `ask` in every preset):
| Row | Strict | Balanced (recommended) | Autonomous |
|---|---|---|---|
| main, unknown | default | default | default |
| manager | read, agents allow; rest default | same | same |
| architect, researcher | read allow; web ask; edit/shell deny | read, web allow; edit/shell deny | read, web allow |
| coder / work-tier customs | read allow; rest ask | read, edit, test allow; git, shell, web ask | read, edit, test, git, shell, web allow |
| reviewer | read allow; test ask; edit deny | read, test allow; edit deny; shell ask | read, test, shell allow; edit deny |
| writer / basic-tier customs | read allow; edit ask | read, edit allow; shell deny | read, edit, web allow |
| think-tier customs | as architect | as architect | as architect |

A role's own `tools`/`disallowedTools` still apply: `allow` never grants a tool the agent file doesn't have.

### 2.3 Manifest additions (`manifest.json`, still `version: 1`, new optional field)
```ts
export interface PolicyRecord {
  settingsPath: string;                 // the file written (§2.4)
  backup?: string;                      // copy taken before the first policy write; absent = file didn't exist
  entries: { list: "permissions.allow" | "permissions.ask" | "permissions.deny"; value: string }[]; // only entries WE added
  hook: { group: unknown } | null;      // the exact PreToolUse group object we appended
  keys: Record<string, KeyRecord>;      // scalar keys, e.g. "permissions.defaultMode"
  compiledPath: string;
  appliedAt: string;
}
// Manifest gains: policy?: PolicyRecord
```
- An entry that is already in the user's list isn't added and isn't recorded, so uninstall keeps it.
- Revert removes each recorded entry still present, removes the hook group only if it deep-equals what we wrote (otherwise `keep-modified`, reported), reverts keys with the existing `revertKey`, and prunes lists, sections and `hooks.PreToolUse` that we made empty. If the result deep-equals `backup`, the backup bytes are written back (same rule as `uninstall`).
- New helper `src/install/settings.lists.ts`: `addEntries`, `removeEntries`, `addHookGroup`, `removeHookGroup`, `pruneEmpty`.

### 2.4 What gets written to settings
Target file: user scope → `claudeDir()/settings.json` (the install's file). Project scope → `<projectDir>/.claude/settings.local.json`. That file is personal and gitignored, so an absolute binary path never lands in a committed file, and its allow rules don't wait for trust. `projectDir` must be the git root (Claude Code reads the local file there); otherwise 400.

```json
{
  "permissions": {
    "ask":  ["Bash(git push *)", "Bash(git push)", "Bash(npm publish *)", "Bash(bun publish *)", "Bash(gh release *)",
             "Bash(rm -rf *)", "Bash(rm -r *)", "Bash(vercel *)", "Bash(fly deploy *)", "Bash(docker push *)"],
    "deny": ["Read(**/.env)", "Read(**/.env.*)", "Edit(**/.env)", "Edit(**/.env.*)", "Read(**/*.pem)", "Read(**/*.key)",
             "Read(**/*.p12)", "Read(**/*.pfx)", "Read(**/.envrc)", "Read(~/.ssh/**)", "Read(~/.aws/**)", "Read(**/credentials.json)",
             "Read(**/service-account.json)"]
  },
  "hooks": { "PreToolUse": [ { "matcher": "^(Read|Grep|Glob|LSP|Edit|Write|NotebookEdit|Bash|WebFetch|WebSearch|Agent|SendMessage|TaskStop|mcp__.*)$",
    "hooks": [ { "type": "command", "command": "/Users/me/.local/bin/claude-manager", "args": ["hook", "pre-tool-use"], "timeout": 5 } ] } ] }
}
```
- `command` is `process.execPath` at apply time, so it is always absolute. Running from source (`bun src/cli.ts`) gives `command: <bun>`, `args: [<abs cli.ts>, "hook", "pre-tool-use"]`.
- The matcher is anchored (`HOOK_MATCHER` in `policy.service.ts`) and includes the read tools (Read, Grep, Glob, LSP), so the hook enforces secret and outside-project reads too. Claude Code matches the pattern as a regex, so the anchors stop a name from matching by substring.
- From source the command is refused (409) unless `--dev-hook` or `CLAUDE_MANAGER_DEV_POLICY=1` is set; tests set the env var in `useTempHome`. Product code never reads `NODE_ENV`.
- `allow` stays empty in every preset. Allows are per role and come from the hook. A settings allow would apply to every session.
- `.env.example` is denied too: no allow can override a deny. This is documented in the UI (`Read .env.example via the owner`).

### 2.5 `defaultMode` (decided: not written by default)
The hook removes worker prompts in any mode except plan, so claude-manager doesn't need to change the owner's session mode. Writing `defaultMode` at user scope would change **every** session in every project, including ones that never use the manager. That is a large side effect for little gain. The setup panel offers an opt-in "Also start sessions in Accept edits" (`acceptEdits` only, which is valid at any scope and recorded in `keys`).
- `auto` isn't offered: it doesn't apply from project/local settings, and its classifier interaction with hook allows is unverified (§1.3).
- `bypassPermissions` is **never** offered or written. Doctor warns when it is set by the user (§7).

### 2.6 Compiled snapshot (what the hook reads)
`~/.claude-manager/policy.compiled.json`, written atomically by the apply step and removed on disable:
`{ version: 1, matrix: Record<row, Record<Capability, Decision>>, testCommands: string[], ownerOnly: string[] /* hook-side tokens */, owned: Record<agentFilePath, sha256>, projectDir?: string }`.
The hook never reads config.json, manifest.json or sqlite, so a call reads exactly one small file.

### 2.7 Audit
The hook appends one JSON line per non-`default` decision to `~/.claude-manager/policy-audit.jsonl` (mode 0600, `O_APPEND`, each line < 512 bytes, so the append is atomic):
`{"ts","session_id","agent_id","role","tool","cap","decision","rule","mode"}`. `rule` is a fixed id such as `role:coder.edit`, `owner-only:push`, `secret`, `outside-project`, `compound-shell` or `shadowed`.
**Never written:** `tool_input`, file paths, commands, URLs, `cwd`, `transcript_path`, prompt text. MCP tool names are cut to `mcp__<server>`.
- The hook skips the append when the file is > 20 MiB (sync isn't running). It never fails the decision over audit I/O.
- `sync` (and the dashboard's sync loop) ingests by byte offset using the existing `files` table, rotates the file to `.1` at 5 MiB once it is fully read, and keeps one old file.

Migration (append to `MIGRATIONS`, index 3 → `user_version` 4):
```sql
-- v0.4.0: hook decisions for the Policy audit table; line_hash makes re-reads after rotation idempotent.
CREATE TABLE IF NOT EXISTS policy_decisions (
  line_hash TEXT PRIMARY KEY, ts TEXT NOT NULL, session_id TEXT, agent_id TEXT, role TEXT NOT NULL,
  tool TEXT NOT NULL, cap TEXT, decision TEXT NOT NULL, rule TEXT NOT NULL, mode TEXT
);
CREATE INDEX IF NOT EXISTS policy_decisions_ts ON policy_decisions(ts);
CREATE INDEX IF NOT EXISTS policy_decisions_role ON policy_decisions(role, decision, ts);
```
Retention runs at the end of each sync: delete rows older than 30 days, then keep the newest 200,000 (`POLICY_AUDIT_DAYS`, `POLICY_AUDIT_MAX_ROWS` as named constants).

## 3. Hook protocol (`claude-manager hook pre-tool-use`)

Input (stdin JSON, ≤ 1 MiB read, the rest discarded). Fields used: `tool_name`, `tool_input.file_path | notebook_path | command | subagent_type` (read in memory only, never logged), `agent_id`, `agent_type`, `cwd`, `permission_mode`, `session_id`. Ignored: everything else.

Row selection:
1. `agent_id` absent → row `main` (the owner's own session, including `claude --agent manager`, where `agent_type` is set but this is the owner's seat).
2. Otherwise `agent_type`, validated with `/^[A-Za-z0-9_.:-]{1,64}$/`, then looked up with `Object.hasOwn(matrix, name)`. Not valid or not found → row `unknown`.
3. **Shadow check:** if `<projectDir or CLAUDE_PROJECT_DIR or cwd>/.claude/agents/<name>.md` exists and isn't in `owned` with a matching sha256 → row `unknown`, rule `shadowed`. A repo can't borrow `coder`'s permissions by shipping its own `coder.md`.

Decision order, first match wins:
1. Secret floor: the tool targets a secret path, or a Bash command mentions `.env`, `id_rsa`, `.pem`, `.key`, `.ssh/` or `.aws/` → `deny` (rule `secret`) for every row except `main`, where it's `default` because settings deny rules already cover main.
2. Owner-only floor: a Bash command with a token `push`, `publish`, `deploy` or `release` after `git`/`npm`/`bun`/`gh`/…, or `rm` with `-r` → `ask`, or `deny` if the cell says deny (rule `owner-only:push`). This also catches forms the settings rules miss (`git -C . push`).
3. Map the tool to a capability (§2.1). `edit` outside `projectDir`, or under `.git/`/`.claude/` → treat the cell as `default` (rule `outside-project`). Paths are resolved with `path.resolve`, and existing files or their parent with `realpath`, so symlinks can't escape.
4. `test`/`git` match only a **simple** command: after removing single-quoted spans, no `; & | < > $ \` ( )` or newline remains. Otherwise the call falls to `shell` (rule `compound-shell`).
5. Cell value. `allow`/`ask`/`deny` → output. `default` → no output.

Output: exit 0 always, with stdout either empty (`default`) or
`{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow|ask|deny","permissionDecisionReason":"claude-manager policy: coder may edit project files (Balanced)"}}`.
The reason names the role, the capability and how to change it (`claude-manager policy set coder edit ask`). It never echoes the input.

Exit codes: never 2. A deny is returned as JSON, so Claude sees the reason. Any internal error (bad JSON, missing or corrupt snapshot, a version mismatch) → exit 0 with empty stdout, plus an audit row `decision: "error"` when the audit file is writable.

**Fail mode: fail-open to the normal permission flow** (no `onFailure: block`). A broken hook means workers get prompts again: annoying, not unsafe, because push/secrets are settings rules (§1.2). `onFailure: block` would instead stop every tool call when the binary moves. Doctor flags the broken state (§7), and the dashboard shows it as "Drift".

Performance budget: p95 ≤ 50 ms per call on the release binary (macOS arm64), with a hard `timeout: 5`. To meet it, `cli.ts` checks `argv[0] === "hook"` **before** importing `commands.registry.ts` and dynamically imports only `hook.command.ts` + `policy.eval.ts`. No sqlite, no React, no manifest. A test measures 30 sequential runs of the built binary.

## 4. Security

### 4.1 Threat model
1. **CSRF from a browser tab.** Same as v0.3.0: Host allowlist, then the write guard (Origin, `Sec-Fetch-Site`, token, JSON, 64 KiB). Impact is higher than agent edits: a forged write could make every worker `allow shell`. So every policy write also needs `If-Match` with the etag from the preview (§5), and PUT body `confirm: true`.
2. **Hook binary hijack.** The settings entry holds an absolute path in exec form (no shell, no PATH lookup, no variable expansion). Anyone who can replace `~/.local/bin/claude-manager` can already edit `~/.claude` directly, so that is out of scope. Doctor checks that the registered path exists, is executable, is the running binary, and isn't group/world-writable.
3. **Malicious agent name.** `agent_type` is data from agent files. It is regex-checked, length-capped, looked up with `Object.hasOwn` (no `__proto__`/`constructor` lookups), never used in a path except the shadow check (which only runs after the regex passes and rejects names containing `/` or `..`), and written to the audit as-is only after the regex.
4. **Shadowed role.** A cloned repo ships `.claude/agents/coder.md` with a hostile prompt. That agent gets row `unknown` (§3, step 3). Residual risk: an agent defined via `--agents` or managed settings under a managed name. Doctor's existing shadow check reports file cases.
5. **User tampering with settings.** Hand-removed entries are noticed by doctor ("policy entry missing") and restored by `policy enable`. Hand-edited hook groups are `keep-modified` on revert and reported. The user's own rules are never removed (§2.3).
6. **Managed settings.** `allowManagedHooksOnly`, `disableAllHooks` or `allowManagedPermissionRulesOnly` make the policy ineffective. Doctor reports FAIL, and the UI shows "Blocked by your organization's managed settings" with no Apply button. Managed deny rules always win, and that's fine.
7. **Edit + test = code execution.** A worker allowed to edit and run tests can run any code it writes, via a test file. The UI says so on Balanced and Autonomous. Settings rules and the hook are not a sandbox, and the docs point to sandboxing for a hard boundary.
8. Not covered: other local users/processes, malware, browser extensions.

### 4.2 Write guard reuse
`isPolicyWriteRoute(method, path)` is added next to `isAgentsWriteRoute`. Everything else in `checkWrite` is unchanged, including the `--read-only` 403.

### 4.3 Hook-side input handling
The hook parses paths and commands to decide, holds them in memory only, and never logs or echoes them. Unknown tools → `default`.

### 4.4 Floors nobody can switch off from the UI
`push` can't be `allow` (400 `push is owner-only; use ask or deny`). Secrets deny rules are always written. The `ask`/`deny` lists in §2.4 are constants in `policy.presets.ts`, not config, in v0.4.0.

## 5. API

Types in `src/server/policy.types.ts`:
```ts
export type PolicyStatus = "not_set_up" | "enforced" | "disabled" | "drift" | "blocked";
export interface PolicyRow { row: string; kind: "main" | "preset" | "custom" | "unknown"; cells: Record<Capability, { decision: Decision; source: "preset" | "override" }> }
export interface PolicyResponse { status: PolicyStatus; reasons: string[]; config: PolicyConfig | null; rows: PolicyRow[];
  settings_path: string | null; hook_command: string | null; installed_scopes: ("user" | "project")[]; warnings: string[]; etag: string }
export interface PolicyInput { preset: PresetName; scope: "user" | "project"; overrides?: PolicyConfig["overrides"]; defaultMode?: "acceptEdits" | null; testCommands?: string[] }
export interface SettingsChange { path: string; op: "add" | "remove" | "keep" | "set"; list?: string; value: unknown }
export interface PolicyPreview { changes: SettingsChange[]; settings_path: string; rows: PolicyRow[]; etag: string }
export interface PolicyWriteResult { policy: PolicyResponse; changes: SettingsChange[]; etag: string }
export interface AuditRow { ts: string; role: string; tool: string; cap: string | null; decision: string; rule: string; mode: string | null; session_id: string | null }
```
`etag` = sha256(config.json text + "\0" + target settings text). A user edit to settings between preview and apply → 412.

| Method & path | Body | Success | Errors |
|---|---|---|---|
| `GET /api/policy` | | 200 `PolicyResponse` | |
| `POST /api/policy/preview` | `PolicyInput` | 200 `PolicyPreview` (writes nothing; guarded like a write) | 400, 409 |
| `PUT /api/policy` | `PolicyInput & { confirm: true }` | 200 `PolicyWriteResult` (sets config, writes settings + snapshot, `enabled: true`) | 400, 409, 412, 428 |
| `PATCH /api/policy/rows/:row` | `Partial<Record<Capability, Decision>>` | 200 `PolicyWriteResult` (re-applies when enabled) | 400, 404, 409, 412, 428 |
| `DELETE /api/policy` | | 200 `PolicyWriteResult` (disable: reverts settings, keeps the matrix) | 409, 412, 428 |
| `GET /api/policy/audit?q&role&decision&tool&since&page&size` | | 200 `{ items: AuditRow[]; total; page; size; facets }` (size ≤ 100, default 50) | 400 |

Errors:
- 400: unknown field, bad capability or decision, `push` allow, a `testCommands` entry with shell metacharacters, project scope not at a git root.
- 404: unknown row.
- 409: no install at that scope (`run "claude-manager install --scope <s>" first`), managed settings block hooks or rules, settings file isn't valid JSON (`fix <path> first`).
- 412: stale etag. 428: missing `If-Match`. `PUT` without `confirm: true` → 400.
All writes run inside `withConfigLock` (export it from `config.apply.ts`).

Apply step (`policy.apply.ts`):
1. Lock.
2. Compute the changes (pure).
3. Back up config.json and the settings file (the settings backup only on the first policy write).
4. Write config atomically.
5. Write settings atomically (tmp + rename via `writeJson`), then the snapshot.
6. Record the manifest.
On any I/O error, restore config, settings and snapshot from the backups and rethrow `apply policy: <cause>` (500).

## 7. CLI and doctor

```
claude-manager policy show [--json]                          # status, target file, matrix
claude-manager policy apply <strict|balanced|autonomous> [--scope user|project] [--accept-edits] [--dry-run] [--yes]
claude-manager policy set <row> <capability> <allow|ask|deny|default>
claude-manager policy enable | disable [--dry-run]
claude-manager policy audit [--since 7d] [--role coder] [--decision deny] [--limit 20]
claude-manager hook pre-tool-use                             # internal; not listed in help
```
- `apply` prints the same `SettingsChange` list as the preview. It asks `Apply? [y/N]` on a TTY unless `--yes`, and on a non-TTY it requires `--yes`. It resets overrides (the dry-run shows which ones).
- All mutations go through `policy.service.ts` (pure transforms) + `policy.apply.ts`, like v0.3.0. The parity test compares the CLI and the API.

`uninstall` reverts the policy first when `manifest.policy.settingsPath` belongs to that scope, then the install, so the final compare-with-backup sees the original file.

Doctor (`src/commands/doctor.policy.ts`, `RoutingCheck`-style results):
- warn `no permission policy: workers will prompt you for every tool. Run "claude-manager policy apply balanced"`;
- FAIL hook group missing or edited, binary path missing, not executable or not this binary, or snapshot missing/older than config;
- warn a recorded entry was removed by hand;
- warn `permissions.defaultMode` is `bypassPermissions` in any user/project file (owner-only ask may be skipped);
- info `acceptEdits`/`auto` default: subagent `permissionMode` is ignored (lists externals that set it);
- warn a settings deny rule (bare tool or `Tool(*)`/`Tool(**)`) conflicts with a policy allow ("coder.edit allow has no effect: ~/.claude/settings.json denies Edit"; `// ponytail: bare and full-wildcard rules only`);
- FAIL managed settings block hooks or rules.

## 9. Acceptance criteria (browser unless marked)
1. Fresh HOME with roles installed and no policy: Overview and Agents show the "Workers will ask you for every tool" banner with **Set up policy**. It has no dismiss control.
2. Set up policy → Balanced → Preview lists exactly the §2.4 entries as `+` and the hook command with the absolute binary path. Apply → confirm → the banner disappears and the status is Enforced.
3. **CLI:** `claude-manager policy show` prints the same matrix. `claude-manager doctor` has no policy warnings.
4. **No prompt for an allowed worker edit (manual, real Claude Code):** in a scratch git repo, run `claude --agent manager` in default mode. Ask: "Have coder, in the background, append a line to NOTES.md and run bun test." There is no permission prompt, the file changes, and `#/policy/audit?role=coder` shows `allow Edit` and `allow Bash (test)`.
5. **Push still prompts (manual):** same session, with a local bare repo as `origin`: "Have coder commit and git push." `git commit` prompts first (`git` is `ask` in Balanced); approve it. Then a prompt naming `coder` appears for `git push`. Answer No → nothing is pushed. The audit shows `ask owner-only:push`.
6. Matrix: set coder → shell → Allow and save. The diff shows "no settings change, snapshot only". `echo '{"tool_name":"Bash","tool_input":{"command":"ls -la"},"agent_id":"a1","agent_type":"coder","cwd":"'$PWD'"}' | claude-manager hook pre-tool-use` (**CLI**) prints `"permissionDecision":"allow"`. The `push` select has no Allow option.
7. **Hook hardening (CLI):** the same pipe with `agent_type` `__proto__`, `../../x` or a 300-char name → empty stdout, exit 0. Garbage stdin → empty stdout, exit 0. A hand-placed `.claude/agents/coder.md` in cwd → empty stdout (row `unknown`, audit rule `shadowed`). No audit line contains `ls -la`, `NOTES.md` or a path.
8. **Byte-identical uninstall (CLI):** `shasum -a 256 ~/.claude/settings.json > before` (a file with your own rules, custom formatting and an existing `Read(**/.env)` deny), then `install`, `policy apply balanced --yes`, `uninstall`, then `shasum -a 256 -c before` → OK. Repeat with no settings file at the start → the file doesn't exist after uninstall.
9. **Drift:** remove the hook group by hand → within one poll the banner says Drift with **Repair**, and doctor reports FAIL. Repair restores it.
10. **Security (curl):** `PUT /api/policy` without a token → 403; with a token but `Origin: https://evil.example` → 403; without `If-Match` → 428; stale etag after editing settings by hand → 412; `{"preset":"balanced","scope":"user"}` without `confirm` → 400; `PATCH /api/policy/rows/coder {"push":"allow"}` → 400.
11. **Read-only (browser + curl):** `dashboard --read-only` → no Set up, Enforce, select or Repair controls; the banner shows the CLI hint; every policy write → 403 `dashboard is read-only (started with --read-only)`.
12. Audit page: facets Role/Decision/Tool count correctly, pagination at 50, and 390 shows Time · Role · Decision with no horizontal scroll.
13. **Performance (CLI):** `test/hook.perf.test.ts` passes, over 30 runs of the built binary: the strict p95 ≤ 50 ms check runs with `CM_PERF_STRICT=1`; the default run asserts a 150 ms sanity bound.
14. **Parity (CLI):** `policy apply balanced --yes` + `policy set coder shell allow` vs `PUT` + `PATCH` on a second temp HOME → identical config.json, settings bytes and snapshot.

## 10. Risks
- **Bash text matching is not a boundary.** Owner-only detection is heuristic (§3, step 2) on top of settings rules. Strict and Balanced keep `shell` at ask. Documented, not hidden.
- **Edit + test can run code** (§4.1, item 7). Balanced accepts this. Strict doesn't.
- **Per-call process spawn** for every matched tool. Mitigated by the matcher, the fast path and the 50 ms budget. Later: move to PermissionRequest once its subagent behaviour is documented (fires only when a prompt is due).
- **Claude Code changes** to hook fields or precedence. Doctor checks the hook entry shape, and the hook ignores unknown fields. A schema change ends in fail-open, which means prompts.
- **Main session in plan mode**: hook allows have no effect on edits, so workers prompt. Doctor/UI note: "In plan mode, workers still ask."
- **One policy at a time** (user or one project). `// ponytail: single policy; per-project policies if owners ask.`

## 11. Decisions (owner-approved 2026-11-28, "setuju")
1. Default scope is user scope (`~/.claude/settings.json`). Project scope writes `.claude/settings.local.json`, never the committed file.
2. `permissions.defaultMode` is not written by default. Only the opt-in "Accept edits" mode may be written. Auto and bypass are never written.
3. Row `main` (your own session, including `claude --agent manager`) uses `default` in every preset, so you keep Claude Code's normal behaviour where you sit. Only the floors apply.
4. Audit logs allow, ask and deny (not `default`). Rows are kept for 30 days or 200,000 rows, and files rotate at 5 MiB.
5. Hook failure mode is fail-open to the normal prompts (no `onFailure: block`). Push and secrets are enforced by settings rules regardless.
